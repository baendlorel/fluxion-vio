## 1 整体架构

### 1.1 三层进程模型

PM2 采用严格的三层进程架构，各层职责分离、生命周期独立。

| 层级            | 角色                      | 生命周期               | 通信方式          |
| --------------- | ------------------------- | ---------------------- | ----------------- |
| CLI 客户端      | 命令入口，解析用户指令    | 短命（执行完即退出）   | RPC + Pub/Sub     |
| Daemon 守护进程 | God 进程，管理所有 Worker | 常驻（机器存活期间）   | IPC + Unix Socket |
| Worker 业务进程 | 实际运行业务代码          | 受控（由 Daemon 管控） | IPC + 事件总线    |

## 2 Daemon 守护化过程

这是复刻的核心：如何让一个进程脱离终端、永久存活。

### 2.1 判断 Daemon 是否已存活

在启动新 Daemon 之前，先探测是否已有 Daemon 在运行。

**实现方式**：尝试连接 RPC Unix Socket，连接成功说明 Daemon 存活。

```js
// === Client.js: pingDaemon() ===
function pingDaemon(cb) {
  var req = axon.socket('req');
  var client = new rpc.Client(req);

  // 连接失败 → 触发 reconnect attempt → Daemon 不存在
  client.sock.once('reconnect attempt', function() {
    client.sock.close();
    cb(false);  // Daemon 未运行
  });

  // 连接成功 → Daemon 存活
  client.sock.once('connect', function() {
    client.sock.close();
    cb(true);   // Daemon 已运行
  });

  req.connect(this.rpc_socket_file);  // ~/.pm2/rpc.sock
}
```

**复刻要点**：
- 使用 Unix Domain Socket 作为探活通道（Linux 原生，无网络开销）
- Socket 文件路径固定（如 `~/.mydaemon/rpc.sock`），作为 Daemon 的唯一标识
- 不要用 TCP 端口探活（会占用端口、可能有防火墙问题）

### 2.2 守护化三步曲

当 Daemon 不存在时，CLI 通过 `child_process.spawn` 启动 Daemon 进程。

```js
// === Client.js: launchDaemon() 核心代码 ===
var ClientJS = path.resolve(__dirname, 'Daemon.js');

// 将 stdout/stderr 重定向到日志文件（不连终端）
var out = fs.openSync(logFilePath, 'a');
var err = fs.openSync(logFilePath, 'a');

var child = require('child_process').spawn(
  process.execPath,    // node 可执行文件路径
  [ClientJS],          // Daemon.js 脚本
  {
    detached: true,    // 【关键1】创建新进程组，脱离终端
    windowsHide: true,
    stdio: [null, out, err, 'ipc']  // stdin=null, stdout/stderr=文件, ipc=通信
  }
);

child.unref();  // 【关键2】从父进程事件循环移除，允许 CLI 退出

// 【关键3】等待 Daemon 通过 IPC 发回 ready 消息
child.once('message', function(msg) {
  child.disconnect();  // 断开 IPC 通道
  cb(null, child);     // Daemon 启动成功
});
```

#### 2.2.1 `detached: true` 的底层行为

在 Linux 上，`spawn({ detached: true })` 底层调用：

1. `clone()` 创建新进程
2. 子进程调用 `setsid()` 成为新会话的 leader
3. 子进程脱离原终端的控制终端
4. 子进程在新进程组中运行，不会因 CLI 退出收到 SIGHUP

这等价于传统 Unix 守护进程的标准操作：`fork() → setsid() → fork()` 的简化版本。

#### 2.2.2 `child.unref()` 的作用

正常情况下，Node.js 父进程会在事件循环中保持对子进程的引用，父进程不会退出直到子进程退出。调用 `unref()` 后：
- 父进程的事件循环不再等待子进程
- CLI 可以执行完命令后立即退出
- Daemon 继续在后台运行

#### 2.2.3 stdio 重定向

- `stdin: null` → 不连接任何输入，避免因终端关闭收到 EOF
- `stdout → 文件` → 日志写入 `~/.pm2/pm2.log`
- `stderr → 文件` → 同上
- `ipc` → 建立父子进程间的 IPC 通道，用于握手

### 2.3 IPC 握手确认机制

Daemon 端在完成初始化后，通过 `process.send()` 向 CLI 报告就绪状态。

```js
// === Daemon.js: sendReady() ===
Daemon.prototype.sendReady = function(cb) {
  if (this.rpc_socket_ready && this.pub_socket_ready) {
    // RPC 和 Pub 两个 Socket 都绑定成功后
    cb(null, { pid: process.pid, pm2_version: pkg.version });

    // 通过 IPC 通道通知父进程（CLI）
    if (typeof(process.send) === 'function') {
      process.send({
        online: true,
        success: true,
        pid: process.pid,
        pm2_version: pkg.version
      });
    }
  }
};
```

### 3.3 domain 全局异常捕获与自愈

Daemon 使用 Node.js `domain` 模块捕获未处理异常，并在崩溃前 spawn 新的替代进程。

```js
// === Daemon.js: start() ===
Daemon.prototype.start = function() {
  var that = this;
  var d = domain.create();

    console.error('[PM2] Resurrecting PM2');

    var path = process.env['_'];
    var fork_new_pm2 = require('child_process').spawn(
      'node', [path, 'update'],
      { detached: true, windowsHide: true, stdio: 'inherit' }
    );

    fork_new_pm2.on('close', function() {
      process.exit(0);  // 旧 Daemon 退出，新 Daemon 接管
    });
  });

  d.run(function() {
    that.innerStart();
  });
};
```

## 4 Linux 信号处理（守护核心）

这是 Daemon 在 Linux 下保持存活的关键机制。

### 4.1 信号注册

```js
// === Daemon.js: handleSignals() ===
Daemon.prototype.handleSignals = function() {
  process.on('SIGTERM', this.gracefullExit.bind(this));   // 终止信号 → 优雅退出
  process.on('SIGINT',  this.gracefullExit.bind(this));   // 中断信号 → 优雅退出
  process.on('SIGHUP',  function() {});                   // 终端关闭 → 忽略（空回调）
  process.on('SIGQUIT', this.gracefullExit.bind(this));   // 退出信号 → 优雅退出
  process.on('SIGUSR2', function() {                      // 用户信号 → 重载日志
    God.reloadLogs({}, function() {});
  });
};
```

### 4.2 各信号行为详解

| 信号    | 回调行为           | 设计意图                                                    |
| ------- | ------------------ | ----------------------------------------------------------- |
| SIGHUP  | **忽略**（空函数） | 防止用户关闭终端时杀死 Daemon。这是 Unix 守护进程的标准做法 |
| SIGTERM | `gracefullExit`    | 外部请求终止时优雅关闭：保存状态、清理资源                  |
| SIGINT  | `gracefullExit`    | Ctrl+C 同上                                                 |
| SIGQUIT | `gracefullExit`    | 同 SIGTERM                                                  |
| SIGUSR2 | `reloadLogs`       | 运维用途：日志轮转后重新打开文件句柄                        |
| SIGKILL | 不可捕获           | 进程被内核直接杀死，无法处理（这是为何需要 domain 自愈）    |

### 4.3 为什么忽略 SIGHUP

当用户关闭终端时，内核会向终端关联的所有进程发送 SIGHUP：

```
用户终端关闭
  │
  ▼
内核向会话内所有进程发 SIGHUP
  │
  ├── CLI 进程 → 收到 SIGHUP → 退出（正常，CLI 本来就短命）
  │
  └── Daemon 进程 → 收到 SIGHUP → 空回调 → 继续运行
      （因为 spawn(detached:true) 已脱离原会话，
        但如果用户手动 kill -HUP 仍能送达，所以仍需忽略）
```

### 4.4 gracefullExit 优雅退出流程

```js
// === Daemon.js: gracefullExit() ===
Daemon.prototype.gracefullExit = function() {
  // 防止并发退出（多个信号同时到达）
  if (this.isExiting) return;
  this.isExiting = true;

  // 1. 通知所有监听者：Daemon 正在关闭
  God.bus.emit('pm2:kill', {
    status: 'killed',
    msg: 'pm2 has been killed by SIGNAL'
  });

  // 2. 杀掉系统信息采集子进程
  if (God.system_infos_proc !== null)
    God.system_infos_proc.kill();

  // 3. 将当前进程列表保存到 dump.pm2（用于后续恢复）
  God.dumpProcessList(function() {

    // 4. 逐个停止所有 Worker
    var processes = God.getFormatedProcesses();
    eachLimit(processes, 1, function(proc, next) {
      God.deleteProcessId(proc.pm2_env.pm_id, function() {
        next();
      });
    }, function(err) {

      // 5. 删除 PID 文件
      fs.unlinkSync(that.pid_path);

      // 6. 退出
      setTimeout(function() {
        process.exit(0);
      }, 2);
    });
  });
};
```

**退出时序图**：

```
信号到达 (SIGTERM/SIGINT/SIGQUIT)
  │
  ├─ 标记 isExiting = true（防重入）
  ├─ 广播 pm2:kill 事件
  ├─ 杀掉系统信息子进程
  │
  ├─ dumpProcessList() ──► 写入 dump.pm2
  │
  ├─ 逐个 deleteProcessId()
  │     └── 每个 Worker: kill → 等待退出 → 清理
  │
  ├─ 删除 pm2.pid 文件
  │
  └─ process.exit(0)
```

### 4.5 `pm2 kill` 的双向信号确认（Linux 特有）

Linux 下 `pm2 kill` 使用 SIGQUIT 实现 Daemon → CLI 的关闭确认：

```js
// === CLI 端: Client.js: killDaemon() ===
Client.prototype.killDaemon = function(fn) {
  // Linux: 监听 SIGQUIT（等待 Daemon 回发）
  if (process.platform !== 'win32' && process.platform !== 'win64') {
    process.once('SIGQUIT', function() {
      quit();  // Daemon 确认已关闭
    });
  }
  // 超时兜底
  var timeout = setTimeout(quit, 3000);

  // 通过 RPC 调用 Daemon 的 killMe 方法
  this.executeRemote('killMe', { pid: process.pid });
};
```

```js
// === Daemon 端: Daemon.js: close() ===
Daemon.prototype.close = function(opts, cb) {
  // 通知关闭
  God.bus.emit('pm2:kill', { status: 'killed', msg: 'pm2 has been killed via CLI' });

  // 关闭 RPC 和 Pub Socket
  that.rpc_socket.close(function() {
    that.pub_socket.close(function() {

      // 【Linux 特有】向 CLI 进程发 SIGQUIT 确认关闭
      if (cst.IS_WINDOWS === false) {
        process.kill(parseInt(opts.pid), 'SIGQUIT');
      }

      // 删除 PID 文件
      fs.unlinkSync(that.pid_path);

      // 退出
      setTimeout(function() {
        process.exit(0);
      }, 2);
    });
  });
};
```

**完整握手流程**：

```
CLI                          Daemon
  │                             │
  │── RPC: killMe(pid=CLI_pid)─►│
  │                             │── 关闭 RPC Socket
  │                             │── 关闭 Pub Socket
  │                             │── 删除 PID 文件
  │◄── kill(CLI_pid, SIGQUIT) ──│
  │                             │
  │  (收到 SIGQUIT)             │── process.exit(0)
  │  → quit()                   │
  │  → 断开连接                  │
  ▼                             ▼
```

### 4.6 Windows 的差异处理

Windows 不支持 Unix 信号系统，PM2 采用不同的策略：

| 功能       | Linux                           | Windows                           |
| ---------- | ------------------------------- | --------------------------------- |
| 通信通道   | Unix Domain Socket (`rpc.sock`) | Named Pipe (`\\.\pipe\rpc.sock`)  |
| 关闭确认   | Daemon 向 CLI 发 SIGQUIT        | CLI 轮询 pingDaemon（间隔250ms）  |
| 进程树杀死 | `ps` + 递归 kill                | `taskkill /pid X /T /F`           |
| 终端关闭   | SIGHUP 忽略                     | 无此问题（Windows 终端无 SIGHUP） |

```js

  that.pingDaemon(function(alive) {
    if (!alive) {
      clearTimeout(timeout);
      quit();
    }
  });
}, 250);
```

```js
// === God.js: handleExit() 完整逻辑 ===
God.handleExit = function handleExit(clu, exit_code, kill_signal) {
  var proc = this.clusters_db[clu.pm2_env.pm_id];
  if (!proc) return false;

  // === 1. 判断是否应该停止重启 ===
  var stopExitCodes = proc.pm2_env.stop_exit_codes || [];
  var stopping = (
    proc.pm2_env.status == 'stopping' ||
    proc.pm2_env.status == 'stopped' ||
    proc.pm2_env.status == 'errored' ||
    proc.pm2_env.autorestart === false ||
    stopExitCodes.includes(exit_code)
  );

  // === 2. 不稳定重启检测 ===
  var min_uptime = proc.pm2_env.min_uptime || 1000;    // 默认 1 秒
  var max_restarts = proc.pm2_env.max_restarts || 16;  // 默认 16 次

  // 如果进程在创建后 (min_uptime * max_restarts) 时间窗口内
  if ((Date.now() - proc.pm2_env.created_at) < (min_uptime * max_restarts)) {
    // 且存活时间不足 min_uptime
    if ((Date.now() - proc.pm2_env.pm_uptime) < min_uptime) {
      proc.pm2_env.unstable_restarts += 1;  // 计数 +1
    }
  }

  // === 3. 超过最大不稳定重启次数 → 标记 errored，不再重启 ===
  var overlimit = false;
  if (proc.pm2_env.unstable_restarts >= max_restarts) {
    proc.pm2_env.status = 'errored';
    proc.process.pid = 0;
    proc.pm2_env.unstable_restarts = 0;
    proc.pm2_env.created_at = null;
    overlimit = true;
    // 通知：重启次数超限
  }

  // === 4. 如果 PM2 自身正在被 kill，不再重启 ===
  if (God.pm2_being_killed) return false;

  // === 5. 计算重启延迟 ===
  var restart_delay = 0;

  // 5a. 固定延迟
  if (proc.pm2_env.restart_delay) {
    proc.pm2_env.status = 'waiting restart';
    restart_delay = parseInt(proc.pm2_env.restart_delay);
  }

  // 5b. 指数退避延迟
  if (proc.pm2_env.exp_backoff_restart_delay) {
    proc.pm2_env.status = 'waiting restart';
    if (!proc.pm2_env.prev_restart_delay) {
      // 第一次退避
      proc.pm2_env.prev_restart_delay = proc.pm2_env.exp_backoff_restart_delay;
      restart_delay = proc.pm2_env.exp_backoff_restart_delay;
    } else {
      // 后续退避：delay × 1.5，上限 15000ms
      proc.pm2_env.prev_restart_delay = Math.floor(
        Math.min(15000, proc.pm2_env.prev_restart_delay * 1.5)
      );
      restart_delay = proc.pm2_env.prev_restart_delay;
    }
  }

  // === 6. 执行重启 ===
  if (!stopping && !overlimit) {
    // 用 setTimeout 实现延迟重启
    proc.pm2_env.restart_task = setTimeout(function() {
      proc.pm2_env.restart_time += 1;
      God.executeApp(proc.pm2_env);  // 重新启动
    }, restart_delay);
  }

  return false;
};
```

### 5.6 重启策略汇总

| 策略           | 配置项                      | 默认值       | 行为                         |
| -------------- | --------------------------- | ------------ | ---------------------------- |
| 基础自动重启   | `autorestart`               | `true`       | 崩溃后自动重启               |
| 固定延迟       | `restart_delay`             | `0`          | 崩溃后等待 N ms 再重启       |
| 指数退避       | `exp_backoff_restart_delay` | 无           | 每次延迟 ×1.5，上限 15s      |
| 退避重置       | `EXP_BACKOFF_RESET_TIMER`   | `30000`(30s) | 稳定运行超过 30s 后重置退避  |
| 最小存活时间   | `min_uptime`                | `1000`(1s)   | 存活不足此时间计为不稳定重启 |
| 最大不稳定重启 | `max_restarts`              | `16`         | 超过后标记 errored 不再重启  |
| 停止退出码     | `stop_exit_codes`           | `[]`         | 退出码匹配时不再重启         |
| 内存超限重启   | `max_memory_restart`        | 无           | 内存超阈值时 reload          |
| Cron 定时重启  | `cron_restart`              | 无           | 按 cron 表达式定时重启       |

## 6 进程终止流程

### 6.1 killProcess 方法

```js
// === God/Methods.js: killProcess() ===
God.killProcess = function(pid, pm2_env, cb) {
  if (!pid) return cb({ msg: 'no pid passed' });

  // 策略1: 优先通过 IPC 消息通知优雅关闭
  if (pm2_env.shutdown_with_message == true) {
    proc.send('shutdown');  // Worker 收到后自行关闭
    return God.processIsDead(pid, pm2_env, cb);
  }

  // 策略2: 非树杀模式 → 直接杀单个 PID
  if (pm2_env.treekill !== true) {
    process.kill(parseInt(pid), cst.KILL_SIGNAL);  // 默认 SIGINT
    return God.processIsDead(pid, pm2_env, cb);
  }

  // 策略3: 树杀模式 → 递归杀整个进程树
  treekill(parseInt(pid), cst.KILL_SIGNAL, function(err, killedPids) {
    pm2_env._tree_pids = killedPids;
    return God.processIsDead(pid, pm2_env, cb);
  });
};
```

### 6.2 processIsDead 超时升级

```js
// === God/Methods.js: processIsDead() ===
God.processIsDead = function(pid, pm2_env, cb, sigkill) {
  var kill_timeout = pm2_env.kill_timeout || 1600;  // 默认 1.6 秒
  var treePids = pm2_env._tree_pids || [pid];

  // 轮询检查进程是否真的死了
  var timer = setInterval(function() {
    if (allDead()) {
      clearInterval(timer);
      clearTimeout(timeout);
      cb(null, true);
    }
  }, pm2_env.kill_retry_time);

  // 超时后升级为 SIGKILL
  timeout = setTimeout(function() {
    clearInterval(timer);

    if (sigkill) {
      // SIGKILL 后仍不死 → 报错
      return cb({ type: 'timeout', msg: 'timeout' });
    } else {
      // 升级：对所有存活进程发 SIGKILL
      var alive = survivors();
      alive.forEach(function(p) {
        process.kill(parseInt(p), 'SIGKILL');  // 不可捕获、不可忽略
      });
      // 递归调用，标记 sigkill=true
      return God.processIsDead(pid, pm2_env, cb, true);
    }
  }, kill_timeout);
};
```

**信号升级链**：

```
SIGINT (可捕获, 允许优雅退出)
  │
  │ 等待 kill_timeout (默认 1600ms)
  │ 期间每 kill_retry_time 轮询一次
  │
  ▼ 进程仍存活
SIGKILL (不可捕获, 内核直接杀死)
  │
  │ 等待 kill_timeout
  │
  ▼ 进程仍存活（极端情况）
报错 timeout
```

### 6.3 TreeKill 的 Linux 实现

```js
// === TreeKill.js (Linux 分支) ===
module.exports = function(pid, signal, callback) {
  // 1. 一次 ps 调用获取所有进程的 pid 和 ppid
  var ps = spawn('ps', ['-e', '-o', 'pid=,ppid=']);

  ps.stdout.on('data', function(data) {
    allData += data.toString();
  });

  ps.on('close', function() {
    // 2. 构建进程树映射：childrenMap[ppid] = [child_pid, ...]
    var childrenMap = {};
    lines.forEach(function(line) {
      var parts = line.trim().split(/\s+/);
      var cpid = parseInt(parts[0]);
      var ppid = parseInt(parts[1]);
      if (!childrenMap[ppid]) childrenMap[ppid] = [];
      childrenMap[ppid].push(cpid);
    });

    // 3. 深度优先收集目标 pid 的所有后代
    var descendants = [];
    function collect(parentPid) {
      var kids = childrenMap[parentPid];
      if (!kids) return;
      kids.forEach(function(kid) {
        collect(kid);           // 先递归子进程
        descendants.push(kid);  // 再记录（后序遍历）
      });
    }
    collect(pid);

    // 4. 自底向上 kill（最深子进程先杀，避免孤儿进程）
    var allPids = descendants.concat(pid);
    allPids.forEach(function(dpid) {
      killPid(dpid, signal);
    });

    callback(null, allPids);
  });
};
```

**为什么自底向上**：如果先杀父进程，子进程会被 init 接管成为孤儿，可能无法正确清理。自底向上确保子进程在父进程之前被终止。

## 7 零停机重载（Graceful Reload）

### 7.1 softReload（软重载）

新 Worker 启动并监听端口成功后，再关闭旧 Worker。

```js
// === God/Reload.js: softReload() ===
function softReload(God, id, cb) {
  var t_key = '_old_' + id;

  // 1. 将旧 Worker 移到临时 key
  God.clusters_db[t_key] = God.clusters_db[id];
  delete God.clusters_db[id];

  var old_worker = God.clusters_db[t_key];

  // 2. 准备新环境
  var new_env = Utility.clone(old_worker.pm2_env);
  God.resetState(new_env);        // 重置 created_at 和 unstable_restarts
  new_env.restart_time += 1;

  // 3. 启动新 Worker
  God.executeApp(new_env, function(err, new_worker) {
    // 4. 等待新 Worker 的 'listening' 事件
    new_worker.once('listening', function() {
      softCleanDeleteProcess();  // 新 Worker 就绪，清理旧 Worker
    });

    // 5. 超时兜底
    var timer = setTimeout(function() {
      softCleanDeleteProcess();  // 超时后也清理旧 Worker
    }, new_env.listen_timeout || 3000);

    // 6. 清理旧 Worker
    function softCleanDeleteProcess() {
      // 6a. 发送 shutdown 消息（优雅关闭）
      old_worker.send('shutdown');

      // 6b. 等待旧 Worker disconnect
      old_worker.once('disconnect', function() {
        God.deleteProcessId(t_key, cb);
      });

      // 6c. 超时后强制删除
      setTimeout(function() {
        God.deleteProcessId(t_key, cb);
      }, 8000);  // GRACEFUL_TIMEOUT
    }
  });
}
```

**softReload 时序**：

```
旧 Worker (处理请求中)
  │
  │ 启动新 Worker
  ▼
新 Worker 启动中...        旧 Worker 继续服务
  │                         │
  │ 'listening' 事件         │
  ▼                         │
新 Worker 开始接客          │
  │                         │
  │── send('shutdown') ────►│
  │                         │── 优雅关闭连接
  │                         │── disconnect
  ▼                         ▼
新 Worker 独占              旧 Worker 清理退出
```
